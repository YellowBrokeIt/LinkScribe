# Media upload spool and queue isolation — 2026-11-28

The original async media-upload handler performed synchronous destination writes on the API event-loop thread, and reserved a job directory and queue slot before rejecting empty or oversized uploads. A scoped baseline run with a real 2 MiB multipart request reproduced identical API-loop and job-creation thread IDs, failing the off-loop regression. The invalid-input regression also failed (the injected unexpected-job assertion caused the test-client portal to terminate).

The replacement synchronous route checks the actual spooled length before reserving a slot, copies in bounded 1 MiB chunks in the FastAPI worker pool, preserves original media bytes and all selected options, and closes the spool before worker submission. A copy failure removes the job and directory. The 150 MiB existing upload cap is unchanged; this is not an ingress limit or a change to recognition.
